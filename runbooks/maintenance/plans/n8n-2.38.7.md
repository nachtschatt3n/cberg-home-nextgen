# n8n: 2.38.4 -> 2.38.7 (patch, stable channel)

## 1. Summary & why this was retargeted

The predecessor plan (`n8n-2.39.0`) targeted 2.39.0, and the reconciler then
flagged it as drifted because 2.39.4 had been published. **Both of those
versions are on the BETA line.** Following the drift to 2.39.4 would have
walked the plan further in the wrong direction.

Channel re-measured **2026-09-12**, from two independent sources that agree:

**npm dist-tags (`npm view n8n dist-tags`):**

    latest  2.38.7
    stable  2.38.7
    beta    2.39.4
    next    2.39.4
    rc      2.39.4

**Docker Hub floating tags, by manifest digest** — the stronger evidence,
because it is the artifact we actually deploy rather than the npm package:

    stable  sha256:a8c95f75c6fdf65f5f2b...   == 2.38.7
    latest  sha256:a8c95f75c6fdf65f5f2b...   == 2.38.7
    next    sha256:5fa13ec66b5703f3ae01...   == 2.39.4
    beta    sha256:5fa13ec66b5703f3ae01...   == 2.39.4
    2.38.4  sha256:5d9f0cc5672b83d438c4...   (running today)

Answering the three questions the retarget had to settle:

- **What does `stable` point at today?** `2.38.7`. It has moved since the deny
  rule was written (that comment records `stable=2.38.5`, measured 2026-09-10)
  — the stable line is advancing normally, two patches in two days.
- **Has 2.39.x been promoted to stable?** **No.** 2.39.4 is simultaneously
  `beta`, `next` and `rc`, and is byte-identical across all three. It is the
  prerelease line, exactly as the rule predicted.
- **What is the correct stable successor to the running 2.38.4?** **2.38.7**,
  confirmed published as a container tag (registry `tags/list`, 5015 tags).

**Therefore the deny rule stays, and is NOT ready to be revisited.** Its own
revisit condition is written on the channel, not the version: *"Revisit when
n8n promotes 2.39.x to stable -- the hold is on the CHANNEL, not the version."*
That has not happened. The rule is currently doing precisely the job it was
added for: `max: patch` holds the 2.39.x beta while still admitting the
2.38.x stable successor.

**Consequence for Renovate PR #213: do not merge it.** It proposes 2.39.4 —
a prerelease wearing a bare semver tag. Renovate tracks registry semver and
cannot see dist-tags, so it will keep re-proposing the beta line every time
2.39.x advances. The PR should be closed or repointed at 2.38.7.

### A correction to the record

The deny-rule comment describes *"a 512Mi SQLite instance"*, and that phrasing
has been read as a memory limit. Measured live 2026-09-12, both numbers exist
and they are different things:

    database.sqlite      512,512,000 bytes  (~489 MiB)  <- this is the 512
    database.sqlite-wal   19,298,112 bytes
    resources.limits.memory    1Gi
    resources.requests.memory  512Mi                    <- and this is a different 512

So: the DB is ~489 MiB, the memory **limit** is **1Gi**, and 512Mi is the
memory **request**. There is no 512Mi memory limit. The coincidence of the two
512s is worth stating plainly because it invites exactly the wrong conclusion
about headroom during a migration.

## 5. Rollback — and the honest limits of the git-revert claim

`rollback_class: git-revert` is **derived for this target, not inherited from
the old plan**, and it rests on one assumption that must be stated rather than
buried: *a 2.38.x patch hop introduces no schema migration that 2.38.4 cannot
read.*

That is the normal case for a patch on a stable line, and it is why this is
rated `low` where the 2.39.0 plan was rated `medium`. But it was **not fully
verifiable offline in this window**: enumerating 2.38.5/2.38.6/2.38.7's
migration set requires pulling those images, which is not a read-only cluster
operation and was out of scope for a replan. What I *can* state is the measured
baseline — **69 bundled sqlite migrations in 2.38.4**, newest
`1787089039727` — against which §4 compares.

**Therefore the pre-check is load-bearing, not ceremonial:** if §4 shows the
migration count increased, `git revert` alone is no longer a complete rollback
and the backup gate's snapshot becomes the real recovery path. Treat a changed
migration count as a reclassification to `backup-restore`, and say so in the
window report rather than letting the frontmatter's `git-revert` stand
unqualified.

```bash
git revert <commit> && git push       # restores tag 2.38.7 -> 2.38.4
# if and only if the migration count moved: restore from the §2 snapshot instead
```

**The six destructive-on-downgrade migrations documented in the old plan are
NOT part of this change.** They belong to the 2.39.x line. They are retained in
§7 because they become live again the moment 2.39 promotes — discarding that
analysis would mean re-deriving it under time pressure later.

## 6. Window / lane placement

This plan is deliberately left `window: null`, because the honest answer is
that **it may not need a window at all**.

2.38.4 -> 2.38.7 is a *patch on the stable line*, which is inside what the
`*n8n*` deny rule already admits (`max: patch`). So it is eligible to land
through the ordinary Step 0 safe-update path, gated by CI and the 48h cooldown
and covered by the engine's own health-gate + auto-revert — the same treatment
every other patch gets. Manufacturing a plan-lane ceremony for it would be
inventing risk that the policy does not assert.

The blocker is purely mechanical: **Renovate is offering the wrong tag.** PR
#213 points at 2.39.4. Until that PR is closed or repointed, the safe path has
nothing correct to merge, and `coverage.py` will keep reporting the n8n row
against the beta target.

Recommended sequence:
1. Close/repoint PR #213 away from the 2.39.x beta line.
2. Let the normal safe-update path take 2.38.4 -> 2.38.7 at a Step 0.
3. Keep this plan only as the written channel analysis + backup gate; retire it
   once the bump lands.

If the operator would rather see the backup gate run under supervision given
the ~489 MiB DB, `sat-attended` is sufficient (risk-load 1, ~20 min). No reboot
is involved, so `allow_reboot: false` is not a constraint.

## 7. Retained: the 2.39.x analysis (applies when 2.39 promotes)

Kept deliberately. When `npm view n8n dist-tags.stable` first reports a 2.39.x
version, this section — not a fresh guess — is the starting point, and the deny
rule's revisit condition fires at the same moment.

- `capability_change: true` for the 2.39 line: workflow **execution semantics**
  change (multi-input nodes re-fired through a loop-back edge run in legacy
  order; all output branches forwarded when a waiting webhook node resumes), the
  Code node "Ask AI" tab is deprecated and hidden, and a retired feature's table
  is dropped.
- `rollback_class: backup-restore`, not git-revert: **2.38.x cannot run on a
  2.39.x schema.** Six new migrations rewrite the ~489 MiB SQLite file in place
  and two are destructive on the way down. The 2026-09-09 measurement found both
  destructive paths affecting zero rows *on this instance* — that is an
  instance-specific, perishable fact and must be re-measured, never assumed.
- The backup gate above is mandatory for that hop, not optional.
