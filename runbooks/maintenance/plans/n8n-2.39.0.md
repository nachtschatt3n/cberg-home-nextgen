Note the near-miss: `nightly:2026-09-10` starts at 03:30, still ~4.8 h short —

**But G5 is not the real reason this needs a window.** The cooldown clears by
itself; the following does not:

**2.39.0 runs six new database migrations, and two of them are destructive in
the DOWN direction.** Established by diffing the migration directories between
the two release tags (`gh api repos/n8n-io/n8n/contents/packages/@n8n/db/src/migrations/{sqlite,common}?ref=n8n@<tag>`):

| dir | 2.38.4 | 2.39.0 | added |
|---|---|---|---|
| `migrations/sqlite` | 68 | 69 | `1788359043381-GeneralizeScheduledJobOwner` |
| `migrations/common` | 207 | 213 | `DropInstanceAiRunSnapshotsTable`, `GeneralizeScheduledJobOwner`, `CreateActivityEventTable`, `CreateProjectPoolSettings`, `CreateInstanceMonitoringReportTable`, `CreateAgentWorkflowDependencyTable` |

Four of the six are plain `CREATE TABLE` (additive, trivially reversible). The
two that matter, quoted from their own source:

- **`DropInstanceAiRunSnapshotsTable`** — `up()` is `dropTable('instance_ai_run_snapshots')`.
  Its own docstring: *"The `down` recreates the table at its final schema … so a
  rollback restores a structurally-identical table — **the historical rows are
  not recoverable**."* Reversible in SHAPE, one-way in CONTENT.
- **`GeneralizeScheduledJobOwner`** — replaces `scheduled_job.workflowId`/`nodeId`
  (and their `ON DELETE CASCADE` foreign key) with `ownerType`/`ownerId`/
  `ownerMemberId`/`orphanedAt`. Its `down()` contains a method literally named
  `deleteJobsTheForeignKeyWouldReject`, commented *"Destructive on purpose"*,
  which `DELETE`s `scheduled_task` rows and then `scheduled_job` rows whose
  workflow has no published version. The SQLite subclass adds
  `withFKsDisabled` with the warning that *"Every column change here recreates
  the whole `scheduled_job` table … up as well as down. `scheduled_task`
  references it with ON DELETE CASCADE, so each recreate's DROP would wipe
  queued tasks."*

So the answer to the question this plan exists to settle: **yes, 2.39.0 runs
schema migrations, and they are effectively one-way — `down()` exists but is
lossy by design on both of the interesting ones.** n8n applies migrations
automatically at startup; there is no opt-out, and the reverse path
(`n8n db:revert`) reverts exactly ONE migration per invocation, must be run
from the NEW image, and would walk straight through both destructive `down()`s.
**§5 forbids it.**

**What softens the risk — and the caveat on it.** The state those two
migrations would damage is, on this instance, EMPTY. Measured read-only against

## 5. Rollback

**Read this before reverting anything.** `git revert` of the tag bump is **not
sufficient and is actively harmful on its own.** After the upgrade the SQLite
file is at the 2.39.0 schema: `scheduled_job` has lost `workflowId`/`nodeId`,
`instance_ai_run_snapshots` is gone, and four tables exist that 2.38.4 has no
entities for. Booting 2.38.4 against that schema is an unsupported
downgrade — n8n will either fail at startup or run against a schema its
repositories disagree with. **The database must be restored with the binary.**

**Do NOT use `n8n db:revert`.** It reverts one migration per invocation, must be
run from the 2.39.0 image, and would execute exactly the two `down()`s quoted in
§1 — the one that deletes `scheduled_task`/`scheduled_job` rows "on purpose" and
the one that recreates `instance_ai_run_snapshots` empty. The file restore is
strictly safer and is why `rollback_class: backup-restore`.

```bash

cd /Users/mu/code/cberg-home-nextgen
git revert --no-edit <sha-of-the-bump-commit>
git show --stat HEAD && git push
flux suspend hr  n8n -n home-automation
flux suspend ks  n8n -n flux-system

# 2. Take the pod down so the RWO volume detaches cleanly
kubectl -n home-automation scale deploy/n8n --replicas=0
kubectl -n home-automation wait --for=delete pod \
  -l app.kubernetes.io/name=n8n --timeout=180s

# 3. Restore the file. Mount the PVC in a throwaway pod (the app pod is gone):
kubectl -n home-automation run n8n-restore --restart=Never --image=busybox:1.37 \
  --overrides='{"spec":{"containers":[{"name":"n8n-restore","image":"busybox:1.37",
   "command":["sleep","3600"],"volumeMounts":[{"name":"d","mountPath":"/data"}]}],
   "volumes":[{"name":"d","persistentVolumeClaim":{"claimName":"n8n-config"}}]}}'
kubectl -n home-automation wait --for=condition=Ready pod/n8n-restore --timeout=120s

kubectl -n home-automation cp "/tmp/n8n-pre-2.39.0-$STAMP.sqlite" \
  n8n-restore:/data/database.sqlite.restore
kubectl -n home-automation exec n8n-restore -- sh -c '
  cd /data &&
  mv database.sqlite database.sqlite.failed-2.39.0 &&
  rm -f database.sqlite-wal database.sqlite-shm &&
  mv database.sqlite.restore database.sqlite &&
  ls -la database.sqlite*'
#   The -wal/-shm MUST go: they belong to the 2.39.0 file and would be replayed
#   onto the restored one.
kubectl -n home-automation delete pod n8n-restore
```

## 6. Interference notes

**Proposed window: `sat-attended:2026-09-19`.** Reasoning, against the live
queue (`maintenance-plan.py --open`, 2026-09-09):

- **`nightly` is wrong on the facts, not on preference.** `rollback_class:
  backup-restore` + `capability_change: true` derives **HUMAN-GATED** under
  `runbooks/autonomy-policy.yaml` (the `auto-backup-gated` class requires
  `capability_change: false`). And §4's strongest assertion is a manual workflow
  execution in the editor — there is no published or scheduled workflow to
  observe, so an unattended run could not verify the thing that matters.
  Additionally `nightly:2026-09-10` at 03:30 is still ~4.8 h inside the G5
  cooldown.
- **`sat-attended:2026-09-12` is full.** It already carries four plans
  (edot-collector 25 + grafana-orphan-dashboard-uid 30 + mcpo-python-3.14 20 +
  scrypted-0.145.0 25 = 100 min) against a 90 min window. Adding 35 min makes
  a bad fit worse.
- **`sun-attended:2026-09-13` fits but is the wrong shape.** 95 of 150 min used
  (absenty 60 + authentik-pg18-lockstep 35); adding 35 leaves a 20 min margin on
  a slot whose other occupant is an auth-datastore lockstep. If either overruns,
  the plan that gets truncated is the one with a 512 MB in-place migration.
- **`sun-attended:2026-09-27` is off limits** — 140 of 150 min is already
  committed to `talos-1.14.0`.
- **`sat-attended:2026-09-19` has 45 of 90 min used** (media-audit-durable-output),
  is attended, needs no reboot, and sits 11 days past the tag's publish date —
  well clear of G5 and long enough for a bad 2.39.0 to have been yanked
  upstream, which is the whole point of the cooldown.

**What the window agent must respect:**

1. **The backup gate is a gate, not a formality.** No tag edit is pushed until
   §2 step 6 prints matching LIVE/COPY counts + `integrity_check ok` **and**
   step 7's two sha256 digests match. If the gate cannot pass, the plan does not
   run — its rollback has no other foundation.
2. **Do not sequence this after another plan that has already consumed the
   window's slack.** The migration step (§3 step 5) must be watched to
   completion; abandoning it half-migrated is the one state neither §4 nor §5
   is written for.
3. **Expect a real outage of this app, briefly.** `strategy: Recreate` on an RWO
   Longhorn volume means the old pod fully terminates first: ~1-3 min of 503 on
   `n8n.${SECRET_DOMAIN}` through `envoy-external`. Nothing else behind that
   Gateway is affected — the HTTPRoute and Gateway are untouched.
4. **Namespace neighbour, not a conflict.** `scrypted-0.145.0` /
   `scrypted-0.146.0` also live in `home-automation`. They share no workload, no
   PVC, no Longhorn volume and no shared infra with n8n, so `conflicts_with` is
   empty by decision rather than by omission. If a Longhorn **engine/control
   plane** plan ever lands in the same window, that IS a conflict (this plan
   writes ~500 MB to and rewrites a Longhorn-backed volume) — none is open today.
5. **`--verify` will not flag this plan as stale by accident**: `current: 2.38.4`
   is what `deploy/n8n` actually runs (verified 2026-09-09, pod Ready 31 h, 0
   restarts). There is no second, older n8n artifact behind this pin — this is
   not a phantom of the kind the plans README lists.
6. **Out of scope, deliberately, and not to be bundled in:** the
   `WEBHOOK_URL → N8N_WEBHOOK_URL` deprecation, the `binaryData → storage` v3
   move (`N8N_MIGRATE_FS_STORAGE_PATH`), the express `trust proxy` setting, and
   the missing Python task runner. All are pre-existing; each deserves its own
   change so that if n8n misbehaves after this window, the cause is one variable.
7. **The dormancy finding in §1 is not this plan's to fix.** Zero published
   workflows is an operator DECISION (re-publish the 8 legacy-active workflows,
   or accept that n8n is editor-only), not a window action. It should be routed
   to the operator separately; do not let this plan's execution be read as
   evidence that n8n's automations are healthy.
