## 1) Summary & why held

Upgrade the Kubernetes control plane (kube-apiserver, kube-controller-manager, kube-scheduler
static pods) and the kubelet on all three nodes (`k8s-nuc14-01/02/03`, 192.168.55.11–.13) from
**v1.36.0** to **v1.36.5**, using Talos' own rolling tool, `talosctl upgrade-k8s`, through the
repo task `task talos:upgrade-k8s`. Talos stays on whatever v1.14.x the nodes run (v1.14.1 today).
etcd stays on 3.7.1. Nothing is rebooted.

### 1.1 What `upgrade-k8s` actually does here

This is from upstream code (`siderolabs/talos` v1.14.1, `pkg/cluster/kubernetes/talos_managed.go`,
`kubelet.go`, `patch.go`), not the docs alone:

1. **Compatibility check.** Talos version against the K8s target, then `upgrade.NewChecks`.
   The path table (`siderolabs/go-kubernetes` v0.2.41, `kubernetes/upgrade/path.go`) keys on
   major.minor. `"1.36->1.36"` is listed, so v1.36.0→v1.36.5 and the rollback v1.36.5→v1.36.0
   are both accepted.
2. **Image pre-pull** (`--pre-pull-images`, default true). It pulls apiserver, controller-manager
   and scheduler onto 3 nodes, plus kubelet onto 3 nodes. **This step is NOT gated on `--dry-run`**
   (`prePullImages` has no DryRun check). A dry-run with the default flags therefore writes to
   every node's image store. The §3.3 dry-run passes `--pre-pull-images=false` for this reason.
3. **Static pods.** For each service in the order apiserver → controller-manager → scheduler, the
   tool works one node at a time. It patches the image in the node's machine config with
   `ApplyConfigurationRequest_NO_REBOOT` (multi-doc aware: `GuessVersionContractKubeAPIServer`
   patches our v1.14 `KubeAPIServerConfig` documents). It then waits until the new static pod
   carries the new config version and is Ready.
4. **kube-proxy.** The tool patches the `KubeProxyConfig` image field. Ours is `enabled: false`
   (Cilium replaces kube-proxy), and `daemonset/kube-proxy` is NotFound (measured), so only a
   config field changes.
5. **Kubelet.** One node at a time, the tool patches the kubelet image (NO_REBOOT). It waits for
   kubelet to go down and come back healthy, then waits for the Node object to report the new
   version and Ready.
6. **Bootstrap-manifest sync** (server-side apply with an inventory, then prune).

Upstream docs (Talos "Upgrading Kubernetes") say: *"Kubernetes upgrades are non-disruptive from
Talos, but Kubelet upgrades may cause workloads to restart."* §4.3 measures whether any workload
container actually restarts.

### 1.2 Upstream evidence: what 1.36.1 to 1.36.5 contain

Sources: `kubernetes/kubernetes` `CHANGELOG/CHANGELOG-1.36.md`, sections "Changelog since
v1.36.0" through "Changelog since v1.36.4". **None of the five patch releases has an "Urgent
Upgrade Notes", "API Change" or "Deprecation" section.** No API is removed or added between
v1.36.0 and v1.36.5. Every Dependencies "Added/Removed" list reads *"Nothing has changed"*, except
1.36.4, which bumps `golang.org/x/*`. The changes that matter for this cluster:

- **1.36.3:** *"Fixed a kubelet memory leak regression in 1.36 caused by leaked contexts on every
  Pod sync."* This affects us: every node has run a 1.36.0 kubelet since 2026-04-30.
- **1.36.3:** *"Fixes a 1.36 regression in server side apply where patching a container type
  (list or map) could result in `422 required` errors for apply requests that previously
  succeeded."* Flux applies everything with SSA.
- **1.36.4:** *"Update golang.org/x/text and golang.org/x/net dependencies to include security
  updates."* Together with the Go toolchain bumps (1.26.4 → 1.26.5 → 1.26.8), this is the content
  behind `security_ref`. The detail stays in the DB.
- **1.36.1:** fixes kubelet deleting the CSI mount directory on a failed periodic
  NodePublishVolume. That needs `requiresRepublish=true`, and both our CSIDrivers
  (`driver.longhorn.io`, `smb.csi.k8s.io`) report `false` (measured), so this fix is not
  load-bearing here.
- The rest is DRA, Windows, kubeadm or kube-proxy fixes. None of those paths is used here (no DRA
  drivers, no Windows, no kubeadm, kube-proxy disabled).

### 1.4 Why held

The `siderolabs/*` deny rule in `runbooks/auto-update-policy.yaml` holds the bump. Its reason
reads *"Talos node image — needs a rolling node-reboot maintenance window"*. **For the kubelet
dep that reason is wrong:** `upgrade-k8s` reboots nothing (§1.1). It is reported as a repo
correction rather than planned around. The hold itself is still right on other grounds: the
upgrade restarts every apiserver and kubelet, the change is an imperative `talosctl` action that
Flux cannot revert, and a git merge alone would only make talconfig drift from the cluster (which
is what past kubelet PRs did).

### 1.5 Ordering vs the Talos roll (`talos-linux-1.14.2`): independent, K8s may go first

- Upstream code says both Talos v1.14.1 and v1.14.2 accept K8s 1.32.0–1.37.99
  (`talos114.go`, quoted in `talos-linux-1.14.2` §1.1). The live dry-run confirmed v1.14.1 accepts
  1.36.5. Sidero's upgrade docs prescribe no Talos-vs-K8s order beyond "Talos must support the
  target".
- The Talos plan states *"Explicitly NOT in this window: `task talos:upgrade-k8s`"*, so the two
  were never meant to share a slot.
- **Recommendation: run this plan first.** It is reboot-free and can take the next sat-attended
  slot or an operator NOW run. It brings forward the kubelet leak fix and the security driver
  without waiting for a free exclusive Sunday. The only cost is a documented one-token amendment
  to `talos-linux-1.14.2` (§6).

- **Slot choice: reboot-free.** `needs_reboot: false`, est 55 min. That fits the

  ceiling, reboot not allowed, which is fine here). It does **not** belong in the Sunday slot with
  `talos-linux-1.14.2`: 165 + 55 = 220 > 180 schedulable, that plan is `exclusive: true`, and its
