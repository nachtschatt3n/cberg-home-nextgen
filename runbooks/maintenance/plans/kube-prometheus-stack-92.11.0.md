### New since the 92.2.0 draft: kube-webhook-certgen 1.8.9 → 1.11.0

Upstream releases (jkroepke/kube-webhook-certgen, 2026-10-14): v1.9.0 adds architectures. v1.10.0 (PR #187) says
"Patch all objects exclusively with server-side apply (field manager `kube-webhook-certgen`)". From the PR body:
"Patching now requires `get, patch` on webhook configurations … kube-prometheus-stack already grants `get, update,
patch` … so no chart change is required." The PR code applies with `Force: true` and sets `failurePolicy` only when
`--patch-failure-policy` is non-empty. Our job passes it empty, so the live `failurePolicy: Ignore` stays. v1.11.0 adds
opt-in `kubernetes.io/tls` secrets and is off by default. The secret stays `Opaque` with `ca/cert/key`.

Checked live on 2026-10-19:
- The rendered ClusterRole `kube-prometheus-stack-admission` grants `get, update, patch` on both webhook kinds.
- The `kube-webhook-certgen` field manager is already present on both configurations.
- The `caBundle` sha256 prefix `b626675342f066ce` equals the `ca` key of secret `kube-prometheus-stack-admission` on all
  3 webhooks.

If the patch hook did fail, the helm upgrade would fail. The HR's `upgrade.remediation.retries: 3` would then roll back
to 91.9.0 automatically, and §4.1 (`helm history` + HR chartVersion) catches that.

## 5) Rollback

**Trigger:** any §4 FAIL, a Prometheus or AM pod not `2/2` within 10 min of the merge, any TSDB error in 4.2, or
`missing` non-empty in 4.3.

**Why a revert is sufficient:** nothing forward-only happens. The CRDs are byte-identical, the
Prometheus/AM/operator images are unchanged, there are no values changes, and the TSDB/AM on-disk format is unchanged.
The certgen create hook reuses the existing CA secret and does not rotate it. A revert removes the nodeSelector again,
which costs one more restart of each pod, and the 91.9.0 hooks run certgen 1.8.9 against the same secret.

```bash
cd /Users/mu/code/cberg-home-nextgen
git fetch origin main && git merge --ff-only origin/main
SHA=$(git log -1 --format=%H -S'version: 92.11.0' -- kubernetes/apps/monitoring/kube-prometheus-stack/app/helmrelease.yaml)
test -n "$SHA" || { echo "NO LANDING COMMIT FOUND - stop"; }
echo "$SHA"; git show --stat "$SHA" | head -8      # must be the #309 squash or the fallback commit
git revert --no-edit "$SHA"
git log -1 --format=%s
git show --stat HEAD     # exactly helmrelease.yaml
git push origin main
```
(`-S` finds the commit that introduced the string, whichever path landed it, merge or fallback.)

**Confirm the cluster is back:** re-run §4.1 and expect `True 91.9.0 v0.94.1`, all three `ns=` empty, and pods
`Running` with fresh start times. Then re-run §4.3, using the same floor rule and silence check against the original
`/tmp/kps9211-silences-before.txt`, and §4.4's caBundle check.

**Special case: Helm already auto-rolled back** (a hook failed and `upgrade.remediation` restored 91.9.0). The HR then
reads 91.9.0 while git says 92.11.0, so the next reconcile will retry. Revert in git anyway, using the steps above, so the
desired state matches. Then capture the hook job logs from the HR events
(`kubectl describe helmrelease -n monitoring kube-prometheus-stack`) for the re-plan.

**Special case: a pod stuck Pending on the selector** (a node lost its `kubernetes.io/os` label). The revert removes the
selector and the pod schedules again. Do NOT hand-label nodes or patch the CR: the operator reverts CR edits, and node
labels on Talos come from the machine config. Investigate the node separately.

**Special case: caBundle mismatch after a successful upgrade.** This does not block alerting (`failurePolicy: Ignore`),
but it disables PrometheusRule admission validation. Revert as above. The 91.9.0 post-upgrade hook re-patches the
caBundle from the unchanged secret, and §4.4's hash check confirms it.

**If an AM restart loses state anyway** (not expected, given the PVC): re-create the silences from the ids and end
times in `/tmp/kps9211-silences-before.txt` via the AM UI or API history. If the PV itself is damaged, the Longhorn
volume `alertmanager-kube-prometheus-stack` has a daily backup (§2.5). Follow the volume restore in
`docs/sops/backup.md`, which is an operator-present step.
