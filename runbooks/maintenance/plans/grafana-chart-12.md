# Grafana stage 3/4 — chart 11.6.1 → 12.10.4 (application STILL held at Grafana 12.4.8)

## 1) Summary & why held

Stage 3 of 4. This crosses the chart major where upstream flips its default
application to Grafana 13 — and **we keep our `image.tag: "12.4.8"` pin so the
application does not follow.** After this stage the chart is current and the app
is still Grafana 12; taking Grafana 13 is stage 4 (`grafana-13-app`), alone, with
its own backup and rollback.

**The upstream note that makes this stage look scarier than it is.** The chart
README's `### To 12.0.0` reads: *"Grafana 13 is configured by default. Grafana 13
explicitly requires an image renderer token, which will be generated by the chart
if not provided."* Both halves are handled:

- *"Grafana 13 by default"* — only via `appVersion`, which `image.tag` overrides.
  Our render stays on `grafana/grafana:12.4.8`.
- *"image renderer token"* — the new `templates/image-renderer-secret.yaml` is
  guarded by `if and .Values.imageRenderer.enabled .Values.imageRenderer.service.enabled ...`.
  `imageRenderer.enabled` defaults to **false** and our values never set it, so no
  renderer object is rendered at all. Verified against chart 12.10.4 on 2026-08-15.

**Values compatibility, checked rather than assumed.** A top-level values-key diff
11.6.1 → 12.10.4 shows **zero removed keys**; added keys are `listenerSet`,
`progressDeadlineSeconds`, `shadowBundledPlugins`, `startupProbe` (plus
`persistence.persistentVolumeClaimRetentionPolicy`). No key this HelmRelease sets
was renamed or dropped. New templates in 12.x: `image-renderer-secret.yaml`
(disabled, above), `listenerset.yaml` (Gateway API — unused), `validate.yaml`.

**The CVE pins become no-ops at this chart version — and that is a finding, not a
formality.** Chart 12.10.4 defaults are exactly `k8s-sidecar 2.10.1` and
`curlimages/curl 8.21.0`, i.e. identical to the 2026-08-14 pins. **Keep the pins
in place anyway during this stage** so the only variable is the chart; removing
them is bookkeeping that belongs with stage 4.

| value | our pin | chart 11.6.1 default | chart 12.10.4 default |
|---|---|---|---|
| `image.tag` | `12.4.8` | (appVersion 12.4.3) | (appVersion **13.1.3**) ← held off by the pin |
| `sidecar.image.tag` | `2.10.1` | 2.6.0 | **2.10.1** |
| `downloadDashboardsImage.tag` | `8.21.0` | 8.19.0 | **8.21.0** |

**Running Grafana 12.4.8 on a chart whose appVersion is 13.1.3 is a deliberate,
temporary, and verifiable state** — it is the whole reason this split exists. It
must not become permanent: stage 4 is what finishes the migration.

## 6) Interference notes

- **Out of order:** running this before `grafana-chart-11` skips the 10→11 major
  and merges two chart majors into one un-attributable change — exactly what the
  split exists to prevent. Running it before `grafana-repo-swap` fails outright
  (chart 12.10.4 does not exist in `grafana.github.io`).
- **Never combine with stage 4 (`grafana-13-app`).** Chart-and-app in one window
  is the original 90-minute plan that could not fit, and it also destroys
  attribution: Grafana 13 migrates folders/dashboards into unified storage on
  first start, which is not cleanly reversible.
- **`conflicts_with: kube-prometheus-stack-88`** — shared `monitoring` namespace
  and shared observability surface.
- Grafana restarts (Recreate, ~30–60 s down). Do not co-schedule with any plan
  whose verification depends on dashboards.
- After this stage the repo carries three image pins that equal the chart
  defaults. That is intentional and temporary. If stage 4 is deferred
  indefinitely, note it as drift — a pin that matches the default silently stops
  tracking the chart's future defaults.
