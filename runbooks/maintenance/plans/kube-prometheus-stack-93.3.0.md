### 1.4 CRDs: this time the schemas really change

`crds.enabled: true` plus `install.crds` / `upgrade.crds: CreateReplace` on the HelmRelease: Flux's helm-controller
replaces the 10 `monitoring.coreos.com` CRDs from the chart's `crds` subchart before the upgrade. That is this repo's
equivalent of the `kubectl apply --server-side` step in UPGRADE.md, and it is proven to run here (the live annotation moved
0.94.1 -> 0.94.2 with the last bump). There is no `crds.upgradeJob` and no manual CRD step in this plan.

I parsed both CRD sets and compared every schema path (not a text diff):

- **Nothing is removed** from any of the 10 CRDs. Every change is an added optional field or an added constraint.
- **New optional fields:** `extraScrapeMetrics` (Prometheus, PrometheusAgent, ServiceMonitor, PodMonitor, Probe,
  ScrapeConfig), `alertmanagerConfigFileSystemMode` and global Telegram `botToken`/`botTokenFile` (Alertmanager), route
  `labels` (AlertmanagerConfig).
- **Added constraints, complete list:** (a) CEL rule on AlertmanagerConfig `receivers[].webexConfigs[]`:
  "httpConfig.authorization or httpConfig.bearerTokenSecret is required"; (b) CEL rule on Alertmanager
  `alertmanagerConfiguration.global.telegram` ("botToken and botTokenFile are mutually exclusive"); (c) an enum on
  `web.tlsConfig.clientAuthType` and `clusterTLS.server.clientAuthType`; (d) `minLength`/`maxItems` inside the embedded

- **None applies to a live object:** no AlertmanagerConfig has a webex receiver (ours are two Telegram receivers using a
  `botToken` Secret reference and one webhook receiver), the Alertmanager object has no `alertmanagerConfiguration`, no
  object sets a web/cluster TLS config, and no volumeClaimTemplate carries a status. Premises `no-webex-receiver-exists` and
  `no-web-tls-client-auth-set` re-measure the first and third at run time.
- **Correction to the predecessor's section 6.3:** it described the new CEL rule as applying to "an httpConfig-bearing
  receiver", which would have included our webhook receiver. The rule sits on `webexConfigs` only.
- `prometheusrules` changes in its header only, so its `metadata.generation` must stay; the other nine must move (section 4.3).
