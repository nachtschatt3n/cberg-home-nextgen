### 1.3 Why it is not auto-safe: six migrations, one of them a SQLite table rebuild

Re-measured 2026-09-20 by diffing the migration directories at the exact tags
(GitHub contents API, `n8n@2.38.7` vs `n8n@2.39.8`):

| Directory | 2.38.7 | 2.39.8 | Added |
|---|---|---|---|
| `packages/@n8n/db/src/migrations/common` | 207 | 213 | **6** |
| `packages/@n8n/db/src/migrations/sqlite` | 68 | 69 | 1 (a dialect OVERRIDE of one of the six) |
| `packages/@n8n/db/src/migrations/postgresdb` | 57 | 57 | 0 |

**The three intermediate releases add ZERO migrations.** The `common` directory
listing at `n8n@2.39.5` and at `n8n@2.39.8` is **identical** (diffed
2026-09-20, no lines of difference), and so are the sqlite and postgresdb
counts. So the schema work in 2.38.7 → 2.39.8 is *exactly* the schema work the
2026-09-16 plan assessed for 2.38.7 → 2.39.5 — nothing was added, nothing was
withdrawn. The six, by filename:

1. `1788336311704-DropInstanceAiRunSnapshotsTable.ts` — **drops a table**
2. `1788359043381-GeneralizeScheduledJobOwner.ts` — see below (this is the one with the sqlite override)
3. `1788425788714-CreateActivityEventTable.ts`
4. `1788445119183-CreateProjectPoolSettings.ts`
5. `1788445119184-CreateInstanceMonitoringReportTable.ts`
6. `1788522448804-CreateAgentWorkflowDependencyTable.ts`

**All six run against our SQLite database.** `migration-index-sync.ts` builds a
dialect's index from `[common, <dialect>]` — the `common` directory is not
optional-per-dialect. The sqlite file is an *override* of migration 2 (same
`1788359043381` timestamp), not a seventh migration, so the `migrations` table
gains **6** rows, not 7.

The one that matters, quoted verbatim from the **SQLite override**
(`migrations/sqlite/1788359043381-GeneralizeScheduledJobOwner.ts`):

> Every column change here recreates the whole `scheduled_job` table on SQLite,
> up as well as down. `scheduled_task` references it with ON DELETE CASCADE, so
> each recreate's DROP would wipe queued tasks.

That is why the override sets `withFKsDisabled = true`. The common
implementation generalises a job's owner from `workflowId`/`nodeId` to
`ownerType`/`ownerId`/`ownerMemberId`, backfills owners, then drops the two old
columns with `recreatesOnSqlite: true`. Its own docstring notes the consequence
that makes this `capability_change: true`:

> The dropped foreign key took its `ON DELETE CASCADE` with it, which was the
> only thing removing a workflow's jobs on unpublish. That job now belongs to
> the application: owner modules deprovision explicitly, and a reconciliation
> sweep quarantines what they miss.

**Why this is `medium` and not `high`:** every one of the six implements
`ReversibleMigration` with a real `down()`, the table rebuild copies rows rather
than truncating, `n8n db:revert` exists in the target image's CLI
(`packages/cli/src/commands/db/revert.ts` present at `n8n@2.39.8`, re-confirmed
2026-09-20), and the blast radius is one app. **Why it is not `low`:** the
rebuild runs with foreign keys disabled on a 489 MiB database holding 9 active
workflows, and a mid-migration interruption (a node drain, a Helm rollback) is
exactly the failure the guards in §3.3 and §3.5 exist to prevent.

No `BREAKING CHANGE` block and no `feat!:`/`fix!:` marker appears in any release
body from 2.39.0 to 2.39.8 — the hold is the channel plus the schema work, not a
declared breakage.

#### 1.5.1 "Add v3 breaking change rule for the storage directory rename" (2.39.6, #38636)

**Verdict: advisory only. Changes NOTHING at 2.39.8. Already happening on
2.38.7 today.** This is the item that most looked like a live hazard, and the
release-note line alone would have supported that reading. The code does not.

What the commit actually adds (`c3dcbbe`, three files): a new **reporting rule**
`packages/cli/src/modules/breaking-changes/rules/v3/storage-path-rename.rule.ts`
plus its test and one line in the rule registry. The class is decorated
`@BreakingChangeRule({ version: 'v3' })` and implements only `detect()`,
returning a description and recommendations. It **moves no files**.

The actual rename lives elsewhere and is **older than both versions**:
`packages/core/src/storage.config.ts` has a real `migrateStorageDir()` that
calls `renameSync(oldPath, newPath)`. Diffed 2026-09-20, that file is
**byte-identical at `n8n@2.38.7` and `n8n@2.39.8`** (`diff` returns no
differences). Its own docstring states the gate:

> Migration is opt-in via `N8N_MIGRATE_FS_STORAGE_PATH=true` and will become
> the default in v3.

We do not set that variable (premise `env-set-unchanged`; live process env
re-checked 2026-09-20, `env | grep -iE "PING_TIMEOUT|STORAGE_PATH|BINARY_DATA"`
→ **NONE SET**). Without it the code takes the warn branch, logs a deprecation
warning and **keeps using the old path**.

**Proof it is not a new signal — measured on the RUNNING 2.38.7, 2026-09-20:**

```
kubectl logs -n home-automation deploy/n8n --tail=4000 | grep -ci "storage directory"   # 1
```

and the line itself is already there today:

> `Deprecation warning: The storage directory "/home/node/.n8n/binaryData" will be renamed to "/home/node/.n8n/storage" in n8n v3. To migrate now, set N8N_MIGRATE_FS_STORAGE_PATH=true. …`

**Do not read that warning as a 2.39.8 regression in §4.** It is pre-existing.

The one branch that *aborts startup* (`StoragePathError.taken`) requires the
opt-in flag AND both directories to exist. Re-measured 2026-09-20 on the live
pod: `~/.n8n/binaryData` exists and is **empty** (0 entries, 4.0K), and
`~/.n8n/storage` **does not exist**. Two independent reasons we cannot reach it.

*Latent item for whoever plans n8n v3, not for this window:* the rename becomes
the default in v3, our PVC is mounted as a whole at `/home/node/.n8n` (so the
rename is in-place inside the volume, not a mount change), and `binaryData` is

`rollback_class: backup-restore`. Pick the branch by **how far the migrations
got** — that is the only question that matters.

### 5.1 Failure BEFORE the migrations completed (crash-loop on boot, image won't pull)

The database is untouched, so this genuinely is one revert:

```bash

```

→ `2.38.7`, HelmRelease Ready `True`, and §4.3's two checksums match the frozen
values. Verify from §4.2 that `finished migration` count is `0` before trusting
this branch — **if migrations did run, use §5.2, not this.**

### 5.2 Failure AFTER the migrations completed

A bare `git revert` here is **not** a rollback: 2.38.7 cannot run on a 2.39.8
schema — `DropInstanceAiRunSnapshotsTable` removed a table the old code knows,
and `GeneralizeScheduledJobOwner` dropped `workflowId`/`nodeId` from
`scheduled_job`. Reverse the schema FIRST, while the 2.39.8 image is still
running (only that image knows these migrations):

```bash
# six times — each call reverts exactly the last migration; all six implement down()
for i in 1 2 3 4 5 6; do
  kubectl exec -n home-automation deploy/n8n -- n8n db:revert
done
kubectl logs -n home-automation deploy/n8n --tail=100
```

Then revert the tag as in §5.1 and re-run §4.3's checksums.

**Three cautions, all from the source:** the `down()` of
`GeneralizeScheduledJobOwner` **recreates `scheduled_job` on SQLite again**
(same rebuild, same FK caveat, in reverse) — an interruption there is as bad as
one on the way up. Each `db:revert` is one step with no confirmation of *which*
migration it removed beyond its own log line, so run them one at a time and read
the output. And the 2.39.8 DEK repair (§1.5.4) is **not** undone by
`db:revert` — it rewrites deployment-key rows outside the migration system. That
repair leaves keys in the current wrapped format, which 2.38.7's
`recoverLegacyDek()` also accepts, so it is not expected to block a downgrade;
if credentials fail to decrypt after reverting, go straight to §5.3.
If any revert errors, stop and go to §5.3.

### 5.3 Floor — restore the volume (operator-gated)

Use the §3.2 `VolumeSnapshot n8n-config-pre-2398`, or the nightly Longhorn
Backup CR identified in §2.4, following `docs/sops/backup.md` → **"Restore from
Backup"** → "Bind Restored Volume to Application", the git-tracked case.

**This is why the class is `backup-restore` and not `git-revert`:** a Longhorn
restore lands as a **new volume name**, and per that SOP
`PersistentVolume.spec.csi.volumeHandle` is immutable, as is a bound PVC's
`spec.volumeName`. Our PV/PVC are git-tracked
(`kubernetes/apps/home-automation/n8n/app/pvc.yaml`, `volumeName: n8n-config`,
`storageClassName: longhorn-static` — re-read 2026-09-20), so rebinding means
editing that manifest and deleting/recreating the PVC — not a revert, and not
something to improvise at 04:00. The PV is `Retain`, so the original data is
never destroyed by this path.

### 6.5 What happens to the two OPEN findings when this ships

Stated because the predecessor plan's close-out instructions were wrong, and
because one of these will *look* stuck afterwards:

- **`F-1beea963` (security) WILL auto-close.** Its title carries a backticked
  `` `n8nio/n8n:2.38.7` ``, and `findings_writer.fingerprint()` anchors identity
  on the backticked identifiers when present — so the version is part of the
  identity. Once the image is 2.39.8 the 2.38.7 row stops being emitted and
  resolves on its own; any residual re-files under a **new** id.
- **`F-09588936` (version) will NOT auto-close, and that is expected.** Its
  title has no backticks, so identity falls back to the normalised prose, where
  `_normalize()` replaces every digit run with `<n>` — the id is therefore
  version-agnostic and stable across bumps (the same `F-09588936` has already
  carried `2.36.5 → 2.38.3` and now `2.38.7 → 2.40.3`). After this window it
  will simply re-emit as `2.39.8 → 2.40.3`, because the version oracle tracks
  the absolute-newest tag, which is the 2.40.x **pre-release** we are
  deliberately not chasing (§6.4, `F-51fb8256`). **Do not "fix" this by
  re-targeting the plan at 2.40.x.** It stays open until either the oracle
  learns the channel or 2.40.x is itself promoted to stable.

### 6.6 Shared-worktree collision observed while writing this plan (2026-09-20)

`maintenance-plan.py --validate` passed cleanly at the start of this re-target
and reports **5 errors** at the end of it. **None of them are this plan**, and
none were caused by it — `grep -ci n8n` over the error list returns `0`, and no
plan anywhere references the retired id `n8n-2.39.5` (checked after the rename).

They are **not fixed here** — editing another owner's plan file is out of scope

routine re-target silently breaks. This plan therefore names volatile

`conflicts_with` for the two refs that are genuinely load-bearing and stable
(`talos-1.14.0`, `flux-oci-chart-sources`) — both re-confirmed to resolve.
