That is why the override sets `withFKsDisabled = true`. The common
implementation generalises a job's owner from `workflowId`/`nodeId` to
`ownerType`/`ownerId`/`ownerMemberId`, backfills owners, then drops the two old
columns with `recreatesOnSqlite: true`. Its own docstring notes the consequence
that makes this `capability_change: true`:

> The dropped foreign key took its `ON DELETE CASCADE` with it, which was the
> only thing removing a workflow's jobs on unpublish. That job now belongs to
> the application: owner modules deprovision explicitly, and a reconciliation
> sweep quarantines what they miss.

#### 1.3.2 Migration 9 is irreversible — the in-app rollback is gone (why `risk` is now `high`)

Quoted verbatim from `DropGitConnectionTables.ts` at `n8n@2.40.7`:

> Drops the git-connection tables. The promotions tables replace them, and the
> feature was never released, so there is no data to keep and no down path.

The class `implements IrreversibleMigration` and defines only `up()`. And
`packages/cli/src/commands/db/revert.ts` (**byte-identical** at `n8n@2.39.8`
and `n8n@2.40.7`, and again at `n8n@2.41.7` — re-checked 2026-10-05 — blob
`4b7b8669`) says what happens when you reach it:

```
if (!lastMigrationInstance.down) {
    ... `Cancelled command. The last migration "${...}" was irreversible.`
    logger.error(message);
    return;
}
```

`db:revert` undoes the LAST executed migration only. At the 2.42.7 target it
cannot even start: the last migration, #18 `AddExecutionScopesToCustomRoles`,
is itself irreversible (§1.7.1), so `db:revert` stops immediately and exits 0.
(At 2.40.7, walking back from 262 it would have undone #13, #12, #11, #10, then
**stopped at #9 and exited 0** (the same
log-and-return shape §5 already warns about.) It can never reach #1-#8, so it
can never produce a schema 2.38.7 can open. **The previous §5.2 — six
serialised `db:revert` runs in a maintenance pod — is therefore deleted, not
adapted.** The rollback after migrations have started is a volume rollback:
a Longhorn snapshot revert of `n8n-config` to the §3.2 snapshot (§5.2), with
the nightly backup as the floor (§5.3).

script, against the live 2.38.7 pod) — every table the new migrations delete

**So why `high` and not `medium`, when nothing here holds a row?** Because risk
in this house is rated on what recovery costs, not only on what is expected to
break. Before this re-target, a post-migration failure was reversible in-app
with the pod's own CLI. After it, the same failure means quiescing Flux,
detaching the volume and reverting it in Longhorn — an operator-attended storage
operation. That is the definition of `high`. **Why it is not a reject:** the
blast radius is still one app with no shared infra, every destroyed table is
empty, the snapshot is minutes old and taken on the same volume (no PV
rebinding for the fast path), and the logical export (§3.2a) is an independent
second floor.

### 1.4 Why n8n has been starved — and what must change for this to ever land

The component reached the AUTO lane repeatedly and never shipped:

- **`auto-update-policy.yaml` holds `*n8nio/n8n*` (narrowed from `*n8n*` 2026-09-26) at `max: patch`** (rule still

  Upstream has now promoted 2.39.x to stable, which is precisely the condition
  the rule's own comment names as its revisit trigger: *"Revisit when n8n

  promoted a SECOND minor (2.40.x, at 2.40.5) and a THIRD (2.41.x, at 2.41.3,

- **Renovate can no longer propose it as a PR.** Since `12de99ef`, `n8nio/n8n`
  carries `followTag: "stable"`, so Renovate tracks the channel pointer and
  would now propose 2.42.7 — as a **minor**, which G2 holds against `max: patch`.
- **coverage.py's direct-bump lane also holds it**, for the same reason.

**Both lanes hold. This plan is the only path 2.42.7 can take today** (re-read
2026-10-05: rule still present, `CHANNEL_RULES` empty, so the hold is the
`max: patch` rule alone). For the
bump to land without a hand-written plan every time the stable line moves a
minor, ONE of these has to change, and this is an operator decision, not a
planner's:

- **Option A (recommended): narrow `*n8nio/n8n*` to `max: minor`.** The channel is no
  longer inferred from the version string — `followTag: "stable"` constrains
  Renovate, and coverage's fallback positively confirms the channel pointer by

  points `stable` at a beta would then auto-merge; the rule's author explicitly

- **Option B: keep `max: patch`** and accept a hand-written plan for every

const scan = (rows) => {
  let nodes = 0; const seen = new Map(); const hits = [];
  for (const r of rows) {
    for (const n of JSON.parse(r.nodes)) {
      nodes++;
      const k = n.type + '@' + n.typeVersion;
      seen.set(k, (seen.get(k) || 0) + 1);
      if (DEPRECATED.has(n.type)) hits.push(r.name + ': ' + k);

  return { nodes, seen, hits };

const ctl = scan([{ name: 'CONTROL', nodes: JSON.stringify([{ type: 'n8n-nodes-base.function', typeVersion: 1 }]) }]);
