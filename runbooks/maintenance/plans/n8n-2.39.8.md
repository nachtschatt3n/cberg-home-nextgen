**The three intermediate releases add ZERO migrations.** The `common` directory

2026-09-20, no lines of difference), and so are the sqlite and postgresdb

withdrawn. The six, by filename:

1. `1788336311704-DropInstanceAiRunSnapshotsTable.ts` — **drops a table**
2. `1788359043381-GeneralizeScheduledJobOwner.ts` — see below (this is the one with the sqlite override)
3. `1788425788714-CreateActivityEventTable.ts`
4. `1788445119183-CreateProjectPoolSettings.ts`
5. `1788445119184-CreateInstanceMonitoringReportTable.ts`
6. `1788522448804-CreateAgentWorkflowDependencyTable.ts`

**All six run against our SQLite database.** `migration-index-sync.ts` builds a
dialect's index from `[common, <dialect>]` — the `common` directory is not
optional-per-dialect. The sqlite file is an *override* of migration 2 (same
`1788359043381` timestamp), not a seventh migration, so the `migrations` table
gains **6** rows, not 7. **That is now an exact, checkable number:** the
`migrations` table holds **249** rows today (measured 2026-09-20, §3.1c) and
must hold **255** after the upgrade (§4.2).

The one that matters, quoted verbatim from the **SQLite override**
(`migrations/sqlite/1788359043381-GeneralizeScheduledJobOwner.ts`, re-fetched
from upstream at `n8n@2.39.8` on 2026-09-20):

> Every column change here recreates the whole `scheduled_job` table on SQLite,
> up as well as down. `scheduled_task` references it with ON DELETE CASCADE, so
> each recreate's DROP would wipe queued tasks.

That is why the override sets `withFKsDisabled = true`. The common
implementation generalises a job's owner from `workflowId`/`nodeId` to
`ownerType`/`ownerId`/`ownerMemberId`, backfills owners, then drops the two old
columns with `recreatesOnSqlite: true`. Its own docstring notes the consequence
that makes this `capability_change: true`:

> The dropped foreign key took its `ON DELETE CASCADE` with it, which was the
> only thing removing a workflow's jobs on unpublish. That job now belongs to
> the application: owner modules deprovision explicitly, and a reconciliation
> sweep quarantines what they miss.

#### 1.3.1 The table the rebuild touches is EMPTY on this instance — measured, and it changes what §4 can prove

**`scheduled_job` = 0 rows. `scheduled_task` = 0 rows.** Measured twice on
2026-09-20 by two independent methods against the live 2.38.7 pod:

- a read-only `sqlite3` open of `/home/node/.n8n/database.sqlite`
  (`SELECT COUNT(*)`, §3.1c) — both `0`;
- the `n8n export:entities` run itself, which printed
  `✅ Completed export for scheduled_job: 0 entities in 1 file(s)` and
  `✅ Completed export for scheduled_task: 0 entities in 1 file(s)`.

Three consequences, all of which the previous draft got wrong:

1. **The FK-disabled rebuild has no rows to lose here.** The hazard the

   requires queued tasks. There are none. That is why `risk` stays `medium`
   rather than rising.
2. **No assertion about `scheduled_job` CONTENTS can carry weight in this
   window.** A row-count gate reads `0` before and `0` after, which is the
   textbook gate that cannot fail. The previous draft's byte-count gate was
   worse than inert — see §4.3.
3. **This is a measurement, not a permanent property.** If someone publishes a
   scheduled workflow between now and the window, the table becomes non-empty
   and the gate becomes live again. §3.1c therefore captures the count at
   window time and §4.3 branches on it explicitly.

**Why this is `medium` and not `high`:** every one of the six implements
`ReversibleMigration` with a real `down()`, the table rebuild copies rows rather
than truncating, `n8n db:revert` exists in the target image's CLI
(`packages/cli/src/commands/db/revert.ts` present at `n8n@2.39.8`, source
re-read 2026-09-20), the two tables it rebuilds are empty (§1.3.1), and the
blast radius is one app. **Why it is not `low`:** six migrations still rewrite a
489 MiB database (512 512 000 bytes, re-measured 2026-09-20) holding 15
workflows and 17 credentials, the 2.39.8 DEK repair writes `deployment_key` rows
outside the migration system and is NOT undone by `db:revert` (§1.5.4), and a
mid-migration interruption (a node drain, a Helm rollback) is exactly the
failure the guards in §3.3 and §3.5 exist to prevent.

No `BREAKING CHANGE` block and no `feat!:`/`fix!:` marker appears in any release
body from 2.39.0 to 2.39.8 — the hold is the channel plus the schema work, not a
declared breakage.

### 1.4 Why n8n has been starved — and what must change for this to ever land

The component reached the AUTO lane repeatedly and never shipped:

- **`auto-update-policy.yaml` holds `*n8n*` at `max: patch`** (rule still
  present, premise `policy-rule-still-present`). That rule is correct for its
  stated reason and was written *because* the beta rides the next minor line.
  Upstream has now promoted 2.39.x to stable, which is precisely the condition
  the rule's own comment names as its revisit trigger: *"Revisit when n8n
  promotes 2.39.x to stable — the hold is on the CHANNEL, not the version."*
  That trigger fired at 2.39.5 and is still true at 2.39.8.
- **Renovate can no longer propose it as a PR.** Since `12de99ef`, `n8nio/n8n`
  carries `followTag: "stable"`, so Renovate tracks the channel pointer and
  would now propose 2.39.8 — as a **minor**, which G2 holds against `max: patch`.
- **coverage.py's direct-bump lane also holds it**, for the same reason.

**Both lanes hold. This plan is the only path 2.39.8 can take today.** For the
bump to land without a hand-written plan every time the stable line moves a
minor, ONE of these has to change, and this is an operator decision, not a
planner's:

- **Option A (recommended): narrow `*n8n*` to `max: minor`.** The channel is no

```bash
kubectl exec -n home-automation n8n-dbrevert -- node /tmp/n8n-rowcount.js | grep '^migrations='
```

**The count must fall by exactly 1 each time: 255 → 254 → 253 → 252 → 251 → 250
→ 249. If a run leaves the count unchanged, STOP and go to §5.3.**

**Why the count and not the exit code — this is the trap.** Read from upstream
source at `n8n@2.39.8` (`packages/cli/src/commands/db/revert.ts`): three
branches log an error and then `return` normally — "The database was never
migrated", "I could not find that migration's code in the currently installed
version of n8n", and "the last migration … was irreversible". The command's
`finally` hook then runs `process.exit(error ? 1 : 0)`, where `error` is only
set by a *thrown* exception. **So a `db:revert` that reverted nothing exits 0.**
An exit-code or a "ran six times" check would report a clean rollback over a
database that never moved.

**Step 4 — restore the image and resume Flux.**

```bash
kubectl delete pod n8n-dbrevert -n home-automation
git revert --no-edit <bump-sha>        # restores tag 2.38.7 AND retries: 3
git push origin main
flux resume helmrelease   n8n -n home-automation
flux resume kustomization n8n -n home-automation
```

Helm restores `replicaCount: 1`, so the `kubectl scale` does not need undoing.
Confirm recovery: §4.1 prints `2.38.7`, `migrations=249`, HelmRelease Ready
`True`, and §4.3 criterion 1's two cksums match the frozen values.

**Two cautions that survive this rewrite:** the `down()` of
`GeneralizeScheduledJobOwner` **recreates `scheduled_job` on SQLite again**
(same rebuild, same FK caveat, in reverse) — which is exactly why the writer is
stopped first; an interruption there is as bad as one on the way up. And the
2.39.8 DEK repair (§1.5.4) is **not** undone by `db:revert` — it rewrites
`deployment_key` rows outside the migration system. That repair leaves keys in
the current wrapped format, which 2.38.7's `recoverLegacyDek()` also accepts, so
it is not expected to block a downgrade; if credentials fail to decrypt after
reverting, go straight to §5.3.

### 5.3 Floor — restore the volume (operator-gated)

Use the §3.2 `VolumeSnapshot n8n-config-pre-2398`, or the nightly Longhorn
Backup CR identified in §2.4, following `docs/sops/backup.md` → **"Restore from
Backup"** → "Bind Restored Volume to Application", the git-tracked case.

**This is why the class is `backup-restore` and not `git-revert`:** a Longhorn
restore lands as a **new volume name**, and per that SOP
`PersistentVolume.spec.csi.volumeHandle` is immutable, as is a bound PVC's
`spec.volumeName`. Our PV/PVC are git-tracked
(`kubernetes/apps/home-automation/n8n/app/pvc.yaml`, `volumeName: n8n-config`,
`storageClassName: longhorn-static`; PV `n8n-config`, reclaim `Retain`,
`volumeHandle n8n-config` — all re-read live 2026-09-20), so rebinding means
editing that manifest and deleting/recreating the PVC — not a revert, and not
something to improvise at 04:00. The PV is `Retain`, so the original data is
never destroyed by this path.

If §5.2 was already under way, leave the Kustomization and HelmRelease suspended
until the restored volume is bound, then resume both.
