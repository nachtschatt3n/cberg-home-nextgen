### 1.2 The target is 2.39.5, NOT 2.40.0 — re-measured, four primaries

The trap this plan exists to avoid: **n8n publishes its beta/next/rc channel on
the next MINOR line with no prerelease marker in the tag**, so naive version
logic reads the beta as an ordinary minor bump. A version label on the `stable`
tag alone is not sufficient evidence — that single signal is what produced the
contradiction this plan was dispatched with. All four re-measured 2026-09-16:

| # | Primary source | Result |
|---|---|---|
| 1 | npm dist-tags (`registry.npmjs.org/-/package/n8n/dist-tags`) | `stable=2.39.5`, `latest=2.39.5`, **`rc`/`next`/`beta`=2.40.0** |
| 2 | Docker Hub tag → digest identity | `stable` and `latest` both resolve to `sha256:cfa04788…`, which is byte-identical to the digest of tag `2.39.5`. `next` and `beta` both resolve to `sha256:fba7e81f…` = tag `2.40.0` |
| 3 | Docker Hub push times | `stable` 2026-09-15T10:27:14Z, `latest` 10:27:17Z, `next` 10:27:14Z, `beta` 10:27:12Z — all re-pushed in the SAME minute, and the pointers still diverge by digest. **Push time alone would have said "both fresh"; the digest is the discriminator.** |
| 4 | GitHub Releases `prerelease` flag | `n8n@2.39.5` **false** (2026-09-14T07:36:57Z) · `n8n@2.39.4`, `2.39.3`, `2.39.2`, `2.39.1`, `2.39.0` all **true** · `n8n@2.40.0` **true** (2026-09-15T10:14:44Z) |

**Reading of #4 that settles it:** the 2.39 line was *born* pre-release and was

not. 2.40.0 then took over the pre-release channel the next day.

### 1.3 Why it is not auto-safe: six migrations, one of them a SQLite table rebuild

Measured by diffing the migration directories at the two exact tags (GitHub
contents API, `n8n@2.38.7` vs `n8n@2.39.5`):

| Directory | 2.38.7 | 2.39.5 | Added |
|---|---|---|---|
| `migrations/common` | 207 | 213 | **6** |
| `migrations/sqlite` | 68 | 69 | 1 (a dialect OVERRIDE of one of the six) |
| `migrations/postgresdb` | 57 | 57 | 0 |

**All six run against our SQLite database.** `migration-index-sync.ts` builds a
dialect's index from `[common, <dialect>]` — the `common` directory is not
optional-per-dialect. The six:

1. `DropInstanceAiRunSnapshotsTable` — **drops a table**
2. `GeneralizeScheduledJobOwner` — see below
3. `CreateActivityEventTable`
4. `CreateProjectPoolSettings`
5. `CreateInstanceMonitoringReportTable`
6. `CreateAgentWorkflowDependencyTable`

The one that matters, quoted verbatim from the **SQLite override**
(`migrations/sqlite/1788359043381-GeneralizeScheduledJobOwner.ts`):

> Every column change here recreates the whole `scheduled_job` table on SQLite,
> up as well as down. `scheduled_task` references it with ON DELETE CASCADE, so
> each recreate's DROP would wipe queued tasks.

That is why the override sets `withFKsDisabled = true`. The common
implementation generalises a job's owner from `workflowId`/`nodeId` to
`ownerType`/`ownerId`/`ownerMemberId`, backfills owners, then drops the two old
columns with `recreatesOnSqlite: true`. Its own docstring notes the consequence
that makes this `capability_change: true`:

> The dropped foreign key took its `ON DELETE CASCADE` with it, which was the
> only thing removing a workflow's jobs on unpublish. That job now belongs to
> the application: owner modules deprovision explicitly, and a reconciliation
> sweep quarantines what they miss.

**Why this is `medium` and not `high`:** every one of the six implements
`ReversibleMigration` with a real `down()` (verified in source, all six), the
table rebuild copies rows rather than truncating, `n8n db:revert` ("Revert last
database migration") exists in this image's CLI, and the blast radius is one
app. **Why it is not `low`:** the rebuild runs with foreign keys disabled on a
489 MiB database holding 9 active workflows, and a mid-migration interruption
(a node drain, a Helm rollback) is exactly the failure the guards in §3.3 and
§3.5 exist to prevent.

No `BREAKING CHANGE` block and no `feat!:`/`fix!:` marker appears in any release
body from 2.39.0 to 2.39.5 — the hold is the channel plus the schema work, not a
declared breakage.

### 1.4 Why n8n has been starved — and what must change for this to ever land

The component reached the AUTO lane repeatedly and never shipped. The mechanism,
confirmed live tonight rather than taken from the finding text:

- **`auto-update-policy.yaml` holds `*n8n*` at `max: patch`.** That rule is
  correct for its stated reason and was written *because* the beta rides the
  next minor line. But upstream has now **promoted 2.39.x to stable**, which is
  precisely the condition the rule's own comment names as its revisit trigger:
  *"Revisit when n8n promotes 2.39.x to stable — the hold is on the CHANNEL, not
  the version."* That trigger has fired.
- **Renovate can no longer even propose it as a PR.** Since `12de99ef`,
  `n8nio/n8n` carries `followTag: "stable"`, so Renovate tracks the channel
  pointer. PR #213 auto-closed. Renovate will now propose 2.39.5 — as a
  **minor**, which G2 holds against `max: patch`.
- **coverage.py's direct-bump lane also holds it.** Tonight's run reports the
  n8n `max_rule_fallback` record with `status: "hold"`, `candidate: "2.39.5"`,
  `blocked_target: "2.40.0"` — the fallback correctly identifies the stable head
  and then correctly refuses it, because the rule blocks minors. Meanwhile the
  `needs_plan` row for n8n still carries `target: 2.40.0`, inherited from the
  version snapshot's absolute-newest-tag reading.

**Both lanes hold. This plan is the only path 2.39.5 can take today** — which is
the definition of the starvation, not a workaround for it. For the bump to land
without a hand-written plan every time the stable line moves a minor, ONE of
these has to change, and this is an operator decision, not a planner's:

- **Option A (recommended): narrow `*n8n*` to `max: minor`.** The channel is no
  longer inferred from the version string — `followTag: "stable"` constrains
  Renovate, and coverage's fallback positively confirms the channel pointer by
  digest before emitting a candidate. `max: patch` was written when neither
  guard existed. Residual risk: an upstream mistake that points `stable` at a
  beta would then auto-merge; the rule's author explicitly accepted holding the
  line against that ("Losing the pointer's integrity should cost us a held
  update, not a shipped beta").
- **Option B: keep `max: patch` and accept a hand-written plan for every stable
  MINOR move.** Honest and safe, but it re-enters this exact starvation every
  few weeks, and it is what produced the state where a component sits behind its
  own stable channel with a security driver open against the live image.

**This plan does NOT change the policy.** Executing it leaves the rule intact,
so without an operator decision the *next* stable minor starves identically.
Whoever runs this window should record the A/B choice.

### 4.1 The running binary reports the new version

```bash

```

### 4.2 The six migrations actually ran, and none failed

```bash
kubectl logs -n home-automation deploy/n8n --tail=2000 | grep -ci "migrations in progress"
kubectl logs -n home-automation deploy/n8n --tail=2000 | grep -ci "finished migration"
kubectl logs -n home-automation deploy/n8n --tail=2000 | grep -i "finished migration"
kubectl logs -n home-automation deploy/n8n --tail=2000 | grep -ciE "migration failed|error during migration"
```

PASS: `migrations in progress` ≥ 1, `finished migration` **≥ 6**, the named list
contains `GeneralizeScheduledJobOwner`, and the failure count is `0`.

**Why these exact strings, and why case-insensitive:** they are upstream's own,
read from `migrations/migration-helpers.ts` at the target tag — `Migrations in
progress, please do NOT stop the process.`, `Starting migration
${migrationName}`, `Finished migration ${migrationName}`. Mixed case, so `-i` is
mandatory. **Can fail:** a count of 0 for `finished migration` means the
migrations never ran — which is what a silently-reverted image or a stale pod
looks like from the outside.

## 5) Rollback

`rollback_class: backup-restore`. Pick the branch by **how far the migrations
got** — that is the only question that matters.

### 5.1 Failure BEFORE the migrations completed (crash-loop on boot, image won't pull)

The database is untouched, so this genuinely is one revert:

```bash
git revert --no-edit <bump-sha>        # restores tag 2.38.7 AND retries: 3
git push origin main
```

Confirm recovery: `kubectl exec -n home-automation deploy/n8n -- n8n --version`
→ `2.38.7`, HelmRelease Ready `True`, and §4.3's two checksums match the frozen
values. Verify from §4.2 that `finished migration` count is `0` before trusting
this branch — **if migrations did run, use §5.2, not this.**

### 5.2 Failure AFTER the migrations completed

A bare `git revert` here is **not** a rollback: 2.38.7 cannot run on a 2.39.5
schema — `DropInstanceAiRunSnapshotsTable` removed a table the old code knows,
and `GeneralizeScheduledJobOwner` dropped `workflowId`/`nodeId` from
`scheduled_job`. Reverse the schema FIRST, while the 2.39.5 image is still
running (only that image knows these migrations):

```bash
# six times — each call reverts exactly the last migration; all six implement down()
for i in 1 2 3 4 5 6; do
  kubectl exec -n home-automation deploy/n8n -- n8n db:revert
done
kubectl logs -n home-automation deploy/n8n --tail=100
```

Then revert the tag as in §5.1 and re-run §4.3's checksums.

**Two cautions, both from the source:** the `down()` of
`GeneralizeScheduledJobOwner` **recreates `scheduled_job` on SQLite again**
(same rebuild, same FK caveat, in reverse) — an interruption there is as bad as
one on the way up. And each `db:revert` is one step with no confirmation of
*which* migration it removed beyond its own log line, so run them one at a time
and read the output. If any revert errors, stop and go to §5.3.

### 5.3 Floor — restore the volume (operator-gated)

Use the §3.2 `VolumeSnapshot n8n-config-pre-2395`, or the nightly Longhorn
Backup CR identified in §2.4, following `docs/sops/backup.md` → **"Restore from
Backup"** → "Bind Restored Volume to Application", the git-tracked case.

**This is why the class is `backup-restore` and not `git-revert`:** a Longhorn
restore lands as a **new volume name**, and per that SOP
`PersistentVolume.spec.csi.volumeHandle` is immutable, as is a bound PVC's
`spec.volumeName`. Our PV/PVC are git-tracked
(`kubernetes/apps/home-automation/n8n/app/pvc.yaml`, `volumeName: n8n-config`),
so rebinding means editing that manifest and deleting/recreating the PVC — not a
revert, and not something to improvise at 04:00. The PV is `Retain` (verified),
so the original data is never destroyed by this path.

## 6) Interference notes

### 6.1 Window routing — NOT the unattended nightly slot

`capability_change: true` (§1.3: webhook resume semantics, `Set-Cookie` from
webhook nodes, a hidden editor tab, new scheduled-job ownership behaviour), so
by `runbooks/autonomy-policy.yaml` this is human-gated and must land in an
**attended** window (`sat-attended` or `sun-attended`), not `nightly`. At 45 min
it fits either 90-minute attended slot with room for §5.2. It must **not** go
into `sun-attended:2026-09-27` (talos-1.14.0 claims that whole slot).

### 6.2 Why `conflicts_with` is exactly two entries

Every open plan's frontmatter was read (`maintenance-plan.py --open`, 2026-09-16):

- **`talos-1.14.0`** and **`flux-oci-chart-sources`** — declared, reasons in the
  frontmatter. Both are one-sided declarations; only this field is honoured by
  `window-scheduler.py`, and a prose rule in someone else's §6 schedules
  nothing.
- **`kube-prometheus-stack-91.4.0` is deliberately NOT a conflict.** The usual
  rule — a plan whose verification reads Prometheus must serialize against a
  same-night kps bump — does not apply, because **this plan never reads
  Prometheus**: n8n has no ServiceMonitor and its `/metrics` returns 404
  (measured). §4 reads the pod, the CLI and the app's own HTTP endpoint only.
- **`float-tag-pinning`** lists `home-automation` in its namespaces, but `grep
  -i n8n` over that plan returns **nothing** — n8n is not in its batch. A shared
  namespace alone is not interference.
- **`unpoller-v5.2.5`, `otel-operator-0.21.0`** (monitoring), **`media-*`,
  `jellyfin-12.1`** (media), **`nextcloud*`** (office), **`wazuh-*`**,
  **`external-dns-unowned-cnames`** — no shared namespace, resource or storage
  with this plan.

### 6.3 Blast radius during the window

n8n is single-replica with `strategy: Recreate`, so it is **fully down** from
pod termination until migrations finish and the server boots — plan for a few
minutes, not seconds. Nine workflows are active; any schedule or webhook due in
that gap is missed (the new scheduler's misfire policy governs what happens to
scheduled jobs, but an inbound webhook during the gap simply fails). The
HTTPRoute and `envoy-external` are untouched, so only this hostname's backend is
affected; every other routed app is unaffected.

Also note the HelmRelease sets `podAnnotations.rollme: "{{ randAlphaNum 5 }}"`,
so **any** Helm upgrade of this release rolls the pod — the downtime above is
not specific to a tag change.

The `needs_plan` row for n8n still reports `target: 2.40.0` (the absolute-newest
tag) while the same coverage run's `max_rule_fallback` record correctly names
